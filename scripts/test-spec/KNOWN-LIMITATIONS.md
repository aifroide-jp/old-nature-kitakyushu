# C1/C3 テスト仕様書生成ツールの既知の限界

`node generate.js` が出す `out/test-spec.md`（C1）・`out/l1-checklist.tsv`（C3）を読む前に把握しておくべき制約をまとめる。

## ① データ網羅性（検証済み・問題なし）

- acf-map.yaml 全51ページは、テストケース27件 ＋ CPT集約による非代表メンバー24件で過不足なく全件アカウントされている（0件の取りこぼし）。
- ただしフィールド単位では、全1013フィールド中 image型243件（24%）は ACF差し替えの自動チェック対象外（表示確認＝目視に委ねる設計）。現状、この除外件数は出力上に明記されていない。

## ② 自動チェックの正しさ（構造的な限界）

自動チェックは「壊れていないことの一部証拠」であって「正しく動いていることの証明」ではない。特に以下は自動OKでもすり抜ける可能性がある。

- **ACF差し替え**: デフォルト値の文字列がHTMLに出現するかだけを見ている。ACFフィールドとして正しく紐付いていても、PHPにベタ書きされた同じ文字列でも、どちらも自動OKになる（管理画面で値を変えても反映されない壊れたページを検出できない）
- **リンク遷移**: リンク先が生存している（非404）かだけを見ている。行き先が意図した別のページを指す配線ミス（生きているが宛先が違う）は検出できない
- **フォーム送信**: `wpcf7-form` のタグ出力だけを見ている。フィールド数・種類の一致や、実際の送信成立・メール着信は確認していない（着信確認はC3で人手に委ねている）
- **アクセシビリティ簡易チェック**: `pa11y-report.json` が無い場合は「未実行」表示になる。2026-08-05時点、このレポートは一度も生成されていないため、**このカテゴリは実質ノーカバレッジ**。C1を流し読みすると自動OK/NGに紛れて見落としやすいので注意

これらのうち実害に直結しやすい優先度: リンク遷移の宛先違い ＞ アクセシビリティ未実行 ＞ ACF差し替えのベタ書き誤検知（お手本に忠実な実装であれば起こりにくいため）。

## ③ 実装の移植性（他Ichiki案件で使い回す場合の注意）

- CPT判定・グルーピングは `inc/seed-posts.php` の `$pages` 配列と `nkk_seed_post()` 呼び出しを正規表現でパースして行っている。この配列名・関数名は rules/ichiki.md の固定契約ではなく、本案件のPhase1実装がたまたまその形だっただけ。他案件で書き方が違えば、パースは黙って空配列を返し、ページ種別判定が崩れる（クラッシュはしないが誤判定になる）
- `lib/checks/visual-diff.js` は本案件だけにある `scripts/visual-diff/pages.js` の形式に依存。無い場合は全ページ「visual-diff未実行」として安全に縮退する

## 根本原因メモ

acf-map.yaml（Phase0 scan出力）はページごとのDOM構造しか持たず、「このN件は同じCPT詳細テンプレートを共有する」という構造的な繰り返しパターン情報を持たない。セクション名もモックアップのCSSクラス名（`section_white`/`section_gray`等）由来で、意味的な構造ではない。モックアップ側でCPT候補となる詳細ページ群のセクション構造・id命名を統一しておけば、Phase0のscanの時点で繰り返しパターンを機械的に検出でき、Phase2のテスト範囲決定はもっと単純になる（詳細はメモリー `feedback_ichiki_mockup_structural_consistency` 参照）。

## 実データで見つかった既存の不具合（今回は未対応。C1の「⚠ 要確認」および本文中の自動NG行に記録済み）

- `events/sample.html`（平尾台シャボン玉フェスティバル）に対応する投稿が `seed-posts.php` に無い
- 多くのページでACFフィールドの大半がフロントに出力されていない（例: `活動ブログ` 2/14一致、`活動拠点` 22/34一致）
- イベント「参加申し込み」4ページ（`page-event-apply.php`）がACF 0/7一致・CF7フォーム未検出・他ページからのリンクが404
