# モックアップ制約化による WordPress 変換の自動化 — 検証レポート

対象: nature-kitakyushu / 検証日: 2026-08-10
前提: **複数サイトを継続的にモックアップ → WordPress へ変換していく**運用

---

## 1. 結論（先に）

モックアップを書く時点で構造を宣言させれば、**Phase0（scan）の推測がなくなり、Phase1 の大半がコマンド化できる**。
実測で確認できたことと、まだ確認できていないことを分けて記す。

| | 確認できた | 根拠 |
|---|---|---|
| 見た目を変えずに構造化できる | **YES** | 実物トップページで**差分 0 / 9,002,240 ピクセル** |
| テキストの取りこぼしをゼロにできる | **YES** | 223件すべてを分類。未分類 0 |
| フィールド名のリネーム工程が不要になる | **YES** | `field-map.json` が恒等写像 |
| 制約モックからコマンドでテーマを生成できる | **YES（7ページ構成で）** | 26 PHP 生成 / フィールド 217/217 / `php -l` 全通過 |
| **実物ボリュームのページでコマンド変換できる** | **まだ NO** | nav 構造2件で変換器が停止（§6-A） |

最後の1行が現時点の限界である。**「実物のトップページがコマンドだけで WordPress になる」とはまだ言えない。**

## 2. 何と何を比べたか

| | 内容 |
|---|---|
| **before** | `index.html`（既存モックのトップページ。無改変） |
| **after** | `proposal/mockup-real/index.html`（同じデザイン・同じ文言のまま、制約語彙に従って構造だけ書き直したもの） |

after は before から**テキストを1文字も変えていない**。変えたのは次の3点だけ。

1. ページ内 `<style>` 673行 → `css/page/front.css` に外出し（`<link>` は同じ位置＝カスケード順を保持）
2. `style="…"` 属性 45個 → クラス化（宣言内容は1文字も変えず `front.css` に転記）
3. `data-*` 宣言 124個を追加（属性の追加のみ。既存のタグ・class・テキストは無改変）

### 見た目が同じであることの証明

```
$ node proposal/visual-check/compare.js
index: 差分ピクセル 0 / 9002240 (0.0000%)  PASS
```

フルページスクリーンショット（1280px幅・高さ7,033px）を pixelmatch で比較。しきい値は設けず、**1ピクセルでも違えば FAIL** とした。
（比較時はアニメーションを停止し、スライドショーを1枚目に固定、遅延読み込み画像を全読み込みさせている）

## 3. before / after の実測

### 3-1. 構造

| 指標 | before（既存モック51ページ） | after（制約版・トップ1枚） |
|---|---|---|
| ページ内 `<style>` を持つページ | **37 / 51** | 0 |
| `style="…"` 属性 | **531個** | **0個** |
| class も id も無い `<section>` | 3個 | 0個 |
| 構造宣言（`data-*`） | **0個** | **124個** |
| `<style>` 内の相対 `url()` | 6個 | 0個（外出し時に基準を付け替え済み） |

after の宣言124個の内訳:

| 宣言 | 数 | 意味 |
|---|---|---|
| `data-acf` | 87 | ACF フィールド |
| `data-acf-type` | 29 | 型の明示（導出できない場合） |
| `data-loop-sample` | 13 | デザイン確認用ダミー（変換時に破棄） |
| `data-section` | 10 | セクション（acf-map.yaml の `sections[].id`） |
| `data-loop` / `data-loop-item` | 4 / 4 | CPT 一覧ループ（spot / center / event / news） |
| `data-common` | 3 | header / footer / cta |
| `data-nav` | 2 | グローバル / モバイル |
| `data-page` / `data-acf-url` | 1 / 1 | ページ種別 / リンク先フィールド |

### 3-2. テキストの捕捉率（これが最大の差）

現行の Phase0 scan が出した `acf-map.yaml` と、既存51ページの全テキストを突き合わせた。

```
既存モック 51ページ
  全テキストノード      : 7,407
  acf-map.yaml が捕捉   : 4,537  (61.3%)
  説明できていない      : 2,870  (38.7%)
```

**正確に言うと、2,870件すべてが「取りこぼし」ではない。** ナビのラベルやフォームの見出しは、そもそも ACF フィールドにするものではない。
問題は、**現行の仕組みには「これは nav だから」「これは装飾だから」と分類する手段が無く、どれが本当の漏れなのか誰にも分からない**ことである。

制約版では全件がいずれかのバケットに入る。

```
$ node proposal/scan/scan.js proposal/mockup-real
全テキストノード           : 223
  acf         (ACFフィールド)             :  89
  nav         (WPカスタムメニューで編集)  :  51
  loop_sample (変換時に破棄するダミー)    :  19
  deco        (装飾)                      :  12
  unclaimed   (宣言なし＝暗黙の固定文言)  :  52
分類合計                   : 223
未分類（取りこぼし）       :   0
RESULT: 取りこぼしゼロ
```

`unclaimed` 52件は取りこぼしではなく、**「更新対象外としてお客様と合意すべき文言」のリスト**である。
現行フローにはこのリスト自体が存在しない。

### 3-3. 消える工程

| 工程 | before | after |
|---|---|---|
| 機械命名 → 意味名のリネーム | 必要（`field-map.json` を人が作る） | **不要**（`field-map.json` が恒等写像） |
| CPT 判定 | セクション構成の一致から推定 | `data-cpt` の宣言を読むだけ |
| セクション名の決定 | 祖先探索・クラス名の部分一致で推測 | `data-section` の宣言を読むだけ |
| hero / main の判定 | クラス名の部分一致で推測 | 宣言から確定 |

現行ルール（`.claude/ichiki/rules/ichiki.md`）は、セクション分類について自ら
「意図しないラッパーを拾うことがある」「誤マッチする余地がある」と記し、**人手レビュー対象**としている。
宣言があればこのレビュー自体が消える。

## 4. 改修コスト（多数サイト変換前提）

### 4-A. before 方式（今の作り方のまま WordPress 化する）

1サイトあたりに発生する作業。

| 作業 | 規模（本サイト実測） | 自動化 |
|---|---|---|
| ページ内 `<style>` の外出し | 37ページ | 機械化可（ただし §6-B の落とし穴あり） |
| `style` 属性のクラス化 | 531個 | 機械化可 |
| **どのテキストをフィールドにするかの判断** | **7,407テキストノード** | **不可（人 or AI の判断）** |
| CPT グルーピングの判定 | — | 推定に頼るため誤判定リスクが残る |
| Phase1 の PHP 生成 | 51ページ分 | AI の自由記述 |
| **生成物の検証** | 51ページ分 | **現行ゲートでは検出できない**（後述） |

最後の行が本質的なコストである。現行の検収ゲート（`check-coverage`）は
「acf-map.yaml の全フィールドが `field-map.json` に載っているか」＝**登録漏れ**しか見ておらず、
「登録した値がテンプレートに出力されているか」を見ていない。実際に次の不具合が生まれ、誰にも検出されなかった。

- 活動ブログ: ACF **2/14** 一致
- 活動拠点: ACF **22/34** 一致
- イベント参加申し込み4ページ: ACF **0/7** 一致・CF7 フォーム未検出・他ページからのリンクが404

**サイト数に比例して、この「静かに壊れる」リスクが増える。**

### 4-B. after 方式（制約に従ってモックを書く）

| 作業 | 規模 | 自動化 |
|---|---|---|
| CSS 分離・`style` 属性のクラス化 | — | **モック生成時に規約どおり書けば発生しない** |
| 構造宣言 | 124個/ページ | **モック生成時に AI が入れる**（lint が検査） |
| acf-map.yaml 生成 | — | **コマンド**（`scan.js`） |
| `field-map.json` | — | **不要**（恒等写像） |
| テーマ生成 | — | **コマンド**（`convert.js`。7ページ構成で実証済み） |
| フィールド出力漏れの検証 | — | **コマンド**（`verify-coverage.js`。漏れたら変換器が停止） |

新規サイトでは 4-A の作業が**発生しない**。既存モックを移行する場合のみ 4-A のコストがかかる。

**したがって、この投資が効くのは「これから作るサイト」である。既存サイトの移行を主目的にすると割に合わない。**

## 5. after が「コマンドでいける」根拠

7ページ構成の制約モック（`proposal/mockup/`）で、実際にコマンドのみでテーマを生成した。

```
$ node proposal/converter/convert.js <mockup> <theme>
→ 26 個の PHP を生成

$ node proposal/converter/verify-coverage.js
合計: 217/217        ← 宣言した data-acf が全部 the_field() として出力されている

$ node proposal/converter/verify-structure.js
欠落 0 / モック側 class 出現 388   ← モックの class が生成物から失われていない

$ php -l （生成PHP 26ファイル）
→ 全て構文エラーなし
```

生成されるもの: `functions.php`（CPT登録・メニュー登録）/ `header.php` / `footer.php` / `front-page.php` /
`page-<id>.php` / `archive-nkk_<cpt>.php` / `single-nkk_<cpt>.php` / `inc/acf-*.php` / `inc/seed-cf7.php` / `assets/`

### 設計上の核心: エスケープハッチを作らない

変換器は、宣言が無い・想定外の構造・置換元が見つからない場合に**推測せず停止し、1ファイルも書かない**。

```
$ node proposal/converter/convert.js proposal/mockup <out>
変換エラー: 以下の箇所で変換器が停止しました（黙ってフォールバックしていません）。
  about/strategy.html:169  href="../privacy/index.html" はモック内のどのページにも解決できません
  contact/index.html:80    href="../privacy/index.html" はモック内のどのページにも解決できません
合計 2 件のエラー。テーマは生成していません。
```

これにより、4-A で挙げた「登録したが出力し忘れる」種類の事故が**構造的に発生しなくなる**。
黙って通ることがないため、検収で見逃されることもない。

## 6. まだ言えないこと・見つかった課題

### 6-A. 実物ボリュームのページは、まだコマンド変換できない

`proposal/mockup-real/index.html`（実物トップページの制約版）を変換器に通すと、**2件で停止する**。

```
index.html:47  data-nav の内部構造を認識できません
index.html:96  data-nav の内部構造を認識できません
```

原因: 変換器が対応している nav の形は「単一 `<ul>` のフラットナビ」と「`<div><h?><ul></div>` の繰り返し」の2種類。
実物のナビは `<div class="nav-item"><a>親</a><ul class="dropdown">…</ul></div>` のドロップダウン型と、
モバイル用のアコーディオン型で、どちらにも当てはまらない。

**これは変換器を1つ足せば済む話ではなく、語彙の設計問題である。**
語彙は `data-nav` で「どのメニュー位置か」を宣言させるが、**マークアップの形は宣言させていない**。
そのため変換器が形のバリエーションを有限個サポートするしかなく、実物は必ずそれを超える。
語彙側で nav のマークアップ形状も制約するか、任意形状を出力できる仕組みが要る。

なお、この検証の過程で `<br>` を含む見出し（`都市と自然、<br>近いからこそおもしろい。`）も
変換器を停止させた。日本語の見出しでは常用される書き方であり、実測で既存51ページに**48箇所**ある。
整形タグ（`<br>` `<strong>` 等）に囲まれたテキストを1フィールドとして扱う対応を入れて解消済み。

### 6-B. ページ内 `<style>` の外出しは「単純な移動」ではない

既存モックのトップページの `<style>` は、グローバル CSS の**再宣言と上書き**を含んでいた。

| セレクタ | base.css | ページ内 `<style>` |
|---|---|---|
| `:root` | `--primary` / `--secondary` / `--accent` | `--color-primary` / `--color-secondary` / `--color-accent` ← **別名の同義変数** |
| `.container` | `max-width: var(--max-width)` / `padding: 0 24px` | `max-width: var(--container-width)` / `padding: 0 20px` |
| `.hero` | `height: 70vh` | `height: 100vh` |
| `.persona-grid` | `repeat(4, 1fr)` | `repeat(2, 1fr)` |

つまりページ内 `<style>` は「ページ固有の追加」ではなく、**style.css とは独立した第2のデザインシステム**だった。
カスケード順を保てば描画は同じだが（差分0が示す通り）、規約（二重定義禁止）には適合しない。
**解消には値の統合という設計判断が要り、機械的な移動では済まない。**（lint L17 が21件検出）

以前 CPT 詳細ページ群（`about/spots/*.html` 9枚）の `<style>` が MD5 完全一致だったことから
「既存モックは機械的に畳める」と述べたが、**トップページには当てはまらない**。この見立ては訂正する。

### 6-C. 既存モック自体のアクセシビリティ不具合

制約版に書き直す過程で、既存モックの不具合が2件表面化した（規約側の問題ではない）。

- `index.html:503` イベント画像がリンク内にあるのに `alt=""`
- `index.html:207` 見出しレベルが h1 → h3 に飛んでいる

また、本サイトの WordPress 実装に対する axe-core 検査では **204件の AA 違反**が検出されており、
2026-08-06 時点で1件も修正されていない。**その多くはモックアップ由来と考えられる。**

### 6-D. 語彙が扱いを定義していない要素

実物トップページに存在し、v0.1 の語彙では宣言方法が未定義のもの。

| 要素 | 数 | 本検証での扱い |
|---|---|---|
| `<video>` + `<source>` | 2 | 「更新対象外の固定コンテンツ」とした（ACF 無料版に動画型が無いため） |
| `<iframe>`（YouTube 埋込） | 1 | 同上 |
| `<details>` / `<summary>` | 各3 | `summary` は型導出表に無い |
| カルーセルの無限ループ用複製 | 10 | `aria-hidden` の装飾として扱った（WP 側で複製を再現する宣言が無い） |
| 文中リンクを含む文 | — | `<a>` だけ宣言され地の文が分断される（未解決） |
| パンくずリスト | — | `data-nav` にも `data-common` にも該当しない |

## 7. 検証の再現方法

```bash
# 見た目が同じことの確認（差分0）
node proposal/visual-check/compare.js

# 制約への適合検査（L01〜L21）
node proposal/lint/lint.js proposal/mockup-real
node proposal/lint/lint.js .                    # 既存51ページ（落ちるのが正しい）

# acf-map.yaml / field-map.json 生成 と 取りこぼし検証
node proposal/scan/scan.js proposal/mockup-real proposal/scan/out-real

# テーマ生成（7ページ構成）とその検証
node proposal/converter/convert.js proposal/mockup <out>
node proposal/converter/verify-coverage.js
node proposal/converter/verify-structure.js

# アクセシビリティ（WCAG2AA / axe）
node proposal/a11y/check.js proposal/mockup
```

既存51ページだけを取り出して lint をかけると **740 error / 7,316 warn** が出る
（`proposal/` 配下の制約モックが混ざらないよう、51ページと `css/` だけを別ディレクトリへ複製して計測）。

| ルール | error | 内容 |
|---|---|---|
| L12 | 554 | `style="…"` 属性 |
| L13 | 80 | class 名・属性値に非ASCII（例: `event-card__type-tag--募集中`） |
| L01 | 51 | `<body>` に `data-page` が無い（＝全ページ） |
| L11 | 37 | ページ内 `<style>` タグ |
| L15 | 11 | `alt` の欠落・装飾宣言のない空 alt |
| L18 / L19 / L14 | 3 / 3 / 1 | 見出しレベルの飛び / class も data-* も無い `<section>` / `images/` 外の画像参照 |
| L20 | (warn) 7,316 | 宣言の無いテキスト＝更新対象外かどうか未合意のもの |

これは失敗ではなく、**「今のモックは規約に適合していない」という測定結果**である。ルールを緩めて通してはならない。

## 8. この検証自体の限界

レポートの信頼性のため、この検証で担保できていないことを明記する。

1. **実物ボリュームでの端から端までの変換は未達成**（§6-A）。`mockup-real` は
   「見た目0px差」「取りこぼし0」「acf-map.yaml 生成」までは到達しているが、テーマ生成には至っていない。
2. **検証したページ数が少ない。** 制約モックは7ページ（うち実物由来は1ページ）。51ページ全体では未検証。
3. **`mockup-real` は規約に完全適合していない。** lint で 27 error が残る
   （内訳: L17 二重定義21 / L08 CPT詳細不在4 / L15 alt空1 / L18 見出し飛び1）。
   このうち L15・L18 は既存モック由来の不具合、L08 は1ページだけ切り出した構成上の当然、
   L17 は §6-B の設計判断待ちである。
4. **運用データの振れ幅は未検証。** モックは「合意した1状態」のスナップショットであり、
   L1 が長すぎるタイトルを入れた場合・画像未設定の場合・一覧が0件/100件の場合の挙動は見ていない。
5. **本番環境（エックスサーバー）での検証は未実施。** URL 置換・SSL・メール到達は Local 環境では担保できない。

### 検証中に自分たちが起こした失敗（同種の再発防止のため記録）

- **同じルールを lint と変換器で二重実装し、数時間で乖離した。** 相対パス化の際に lint 側だけ
  正規化を入れ、変換器が取り残されて18件のエラーで停止した。共有モジュールに一本化して解消。
  同種の二重実装が他に4箇所残っている。
- **モック生成プロンプトに「WCAG 2.0 AA を通す前提」と明記したが守られず、31件の違反が出た。**
  プロンプトは制約を守らせられない。ゲートだけが担保になる。
- **アクセシビリティ検査が「判定不能」を「違反」として扱い、合意済みのデザインを変えてしまった。**
  pa11y の既定 `levelCapWhenNeedsReview: 'error'` により、axe の incomplete（＝測定できなかった）が
  エラーに格上げされていた。写真の上の白文字が「測れない」だけなのに、単色パネルに変更する修正が入った。
  設定を変えて人手確認項目として別枠表示するようにし、デザインは元に戻した。
  **検査ツールの都合でデザインを変えると、柱①（モックで合意）と柱②（変換で保つ）の両方が壊れる。**

## 9. 次にやるべきこと（優先順）

1. **nav のマークアップ形状を語彙で制約する**（§6-A）。ここが実物変換の唯一の障壁。
2. **`<style>` とグローバル CSS の変数体系を統合する**（§6-B）。L17 の21件が消える。
3. 語彙 v0.2 で未定義要素を埋める（§6-D）。特に文中リンクとパンくず。
4. lint と変換器の二重実装4箇所を共有モジュールへ寄せる。
5. a11y ゲートをモック生成の受入条件として運用に組み込む（axe 204件の再発防止）。

なお 1〜5 はすべて `proposal/` 内で完結し、**`.claude/ichiki`（Ichiki 本体）にはまだ一切手を入れていない。**
語彙が固まってから移す。
