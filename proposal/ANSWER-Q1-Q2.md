## 回答

**Q1. できます。ただし全部ではありません。**

変更のたびに検査が走り、**修正が一意に決まる違反は AI が直し、デザインの決定を含む違反は止めて人に返す。** この形でループは回ります。ご懸念の31件は配色なので、直させるのではなく**発生前に落とします**（決めた色以外を書けなくする）。

なお、**生成AIにルールを読み込ませることは担保になりません。** 31件はまさに、生成の指示に明記した上で守られなかったものです。担保は検査が走ることであって、指示ではありません。

残る条件は「**検査を回さないまま PR を出し、そのまま取り込まれてしまう状況を防げるか**」の1点で、これは CI が使えるかに依存します。

**Q2. できます。原理的な障害はゼロです。**

現状足りていないのは6項目で、すべて未実装です。順序として、実物ボリュームでの変換を通し切るのが先になります。

## 前提

### 対象範囲

本回答は **`proposal/` の PoC（モックアップ制約化の検証）** を対象とします。既存案件の WordPress テーマ構築（51ページ・`scripts/test-spec/`）は別件です。

**31件と204件は別物です。** 31件は PoC で生成したモックのアクセシビリティ違反。204件は既存案件51ページの未修正違反（`scripts/test-spec/KNOWN-LIMITATIONS.md`）。どちらも件数で語られるため混同されやすく、本回答では31件のみを扱います。

ただし **CI の欠落は両方に共通する穴** です。`.claude/ichiki/rules/ichiki.md` は「pa11y-ci + axe-core を GitHub Actions で実行し、違反があればマージをブロックする」と規定していますが、既存案件でも未達です（204件が残っている理由がこれ）。

### ループは2つあります

| | 入力 | 出力 | 完了条件 |
|---|---|---|---|
| **ループA：モック生成** | 指示・制約語彙 | 合意用モックアップ | 構造検査 0件 ＋ アクセシビリティ検査 0件 |
| **ループB：テーマ生成** | 合意モック | WordPress テーマ | 変換器が停止しない・検収ゲート通過 |

Q1 は31件を引用しているのでループAを指していますが、実運用では両方回ります。性質が違うため、以下では分けて扱います。

### ご懸念の31件について

内訳は **配色コントラスト違反30件 ＋ フレーム関連1件** です。全件が CSS の色指定に由来し、**検出は機械が一意にできます。**

ただし**修正は一意に決まりません。** コントラスト不足は、文字色を濃くする・背景を変える・文字を大きくする、といくつも直し方があり、どれを選ぶかはデザインの決定です。ここを AI に直させると、デザインが書き換わります。

したがって正しい対処は「検出して直させる」ではなく、**発生前に落とす**ことです。31件は axe（ブラウザ必要・13.4秒）で**書いた後に**見つかりました。パレット検査（ブラウザ不要・数十ms）なら、決めた色以外を使った時点で落ちます。**直し方を選ぶ場面自体が発生しません。**

論点は「31件を機械で防げるか」ではありません。防げます。**「検査を通していないものが取り込まれるのを防げるか」の1点**です。

### 本書での「機械的に決まる」

以降で「機械的に決まる」と書いた場合、**同じ入力から必ず同じ結果が出て、人やAIの判断が入らない**ことを指します。逆が「AIの自由記述」です。

## Q1 の答え

### ループはこう回ります

違反を1種類として扱わず、3つに分けます。

| 違反の種類 | 例 | 対処 |
|---|---|---|
| 修正が1つに決まる | 宣言の付け忘れ、命名規則違反、参照パスの書き方、変数化されていない色を既存の変数に置き換える | **AI が直す** （無人で回る） |
| 修正候補が複数ある | 配色コントラスト不足、レイアウトの取り方 | **止めて人に返す** |
| そもそも発生させない | 決めた色以外の使用 | **事前検査で落とす**（直し方を選ぶ場面が来ない） |

**「違反があれば AI が直す」を全域に適用してはいけません。** 修正候補が複数ある違反まで直させると、AI がデザインを変える方に倒れます。

検査には層が2つあります。**ループの中で走らせること自体は、今でもできます。** 実装していないだけで、現在は手で回しているものです。担保が必要なのは「検査を通していないものが取り込まれるのを防げるか」で、これは[別レイヤーの話](#省略防止について)になります。

### 人が要る箇所（＝自動化の境界）

**4種類あります。**

| # | 箇所 | 段 | 性質 |
|---|---|---|---|
| ① | デザインの決定 | 1・2 | **自動化しない。** 修正候補が複数あるとき、選ぶことは決定であり、決定する権限はツールにない |
| ② | 測定できないアクセシビリティ項目 | 2 | **目視で確認する。** 測定手法の限界であり、デザイン側の欠陥ではない |
| ③ | 変換器が停止した時の対処判断 | 3 | **先回りできない。** 停止理由は停止するまで分からない |
| ④ | 表示・レスポンシブ・メール着信の確認 | 5 | 見た目と着信は人の目が要る。ただし段5は未到達のため、**実測ではなく性質からの判断**です |

**ご懸念の31件は、予防に回せば①に触れません。** 発生してから直そうとすると①（デザインの決定）に入り込みます。だから対処を事前検査に置きます。

### ①について

**候補が2つ以上ある時点で停止し、報告のみ行います。** どれを選ぶかはデザインの決定なので、ツールは触りません。

**制約検査の役割は、デザイン判断を近似することではなく、デザイン判断が機械に上書きされないよう守ることです。**

### ③について

停止理由は事前に列挙できないため、ここは人が残ります。**重要なのは対処の方向です。**

`<br>` の件では変換器を拡張して解決しました。実測48箇所ある常用の書き方をデザイン側に諦めさせる選択肢はありません。ナビについても同じ方向で対処します。

> **要件条項：変換器が停止した場合、まず変換器を拡張する。デザイン側の制約は最後の手段であり、その場合はデザイン側の合意を必須とする。**

### 省略防止について

ループの中で検査を走らせることと、検査を通していないものが取り込まれるのを防ぐことは別の話です。**環境に依存するのは後者だけ**です。

**CI が使えれば「省略できない」状態を作れます。** 正確には、PR を出すこと自体は止まりません。PR を出した時点で検査が自動で走り、**通らなければ取り込めない**という止め方になります。誰が忘れても、通っていないことは全員に見えます。

使えない場合の代替は2つあります。

1つ目、**PR に実行結果を記載する運用。** ただし貼られた結果は自己申告で、貼った後にコードを直せばズレます。単体では信用度に欠けます。

2つ目、**検査結果をファイルとして出力し、生成元のコミットハッシュを埋めてコミットに含める。** 古い結果が混ざったときに気づけます。PR テンプレートには実行コマンド（または「README の手順①②を実行してください」の一文）を明記します。

**ただし到達点は「省略したら分かる」までです。** 実行しないこと自体は止められず、照合を誰かが見る必要があります。「省略できない」とは書けません。ここが CI の有無で変わる唯一の点です。

## Q2 の答え：そのうち開発者でないと回らない箇所

Q1 で挙げた4種類の人手のうち、**①②④はデザイナー・運用担当・お客様の仕事**であり、開発者である必要はありません。

**③とその周辺（ルールの追加・変更）だけが、現状の担当者に張り付いています。**

| 属人化している箇所 | 理由 |
|---|---|
| ルールの追加・変更 | 手順書が無い。1本の増減が最大6ファイル11箇所に波及する |
| ルール内容の整合 | 同期チェックが**ルール番号の有無しか見ない**。11箇所のうち何箇所か直し忘れても通る |
| 語彙と生成プロンプトの同期 | 手書きの2ファイル。差分の根拠が説明できない |
| 変換器停止時の判断 | 対処の方針が運用に書かれていない |
| 検証記録の維持 | `REPORT.md` が現状に追いついていない（後述） |
| 構造検査の変更 | テストが0件。壊しても気づかない |

### なぜできていないか

- **テストが0件** — 合格／不合格の検証データは作成済みですが、リポジトリに入れていません。
- **CI・手順書** — 未着手です。
- **生成プロンプトの手書き** — 「制約定義を1つに置いて検査とプロンプトを生成すべき、二重管理すると必ずズレる」と述べた直後に、手で2ファイル書きました。**これは判断ミスで、要修正です。**

### 解消策

| 項目 | 内容 |
|---|---|
| 検証データをリポジトリに入れる | 22ルール × 合格/不合格。作成済みのものを入れるだけ |
| ルール表に「変換上の根拠」列を追加 | 根拠が書けないルールは書いた時点で落ちる |
| ルール追加手順書 | 1ページ。「ルールを1件足す手順」 |
| 語彙から生成プロンプトを自動生成 | 3ファイル同期という問題自体が消える。プロンプトは担保にはならないが、初回精度が上がり往復回数が減る |

- **L07** — 一覧の繰り返しは、見本を1件だけ書く。1件目だけ要素が増えるデザインが書けない
- **L10** — フォームの送信ボタンは1個。2ボタン構成が書けない
- **L12** — HTML に直接スタイルを書かない。要素ごとに違う値を持たせられない
- **L14** — 画像は `images/` の中だけを参照する。地図やSNSの外部埋め込みが書けない

### L22（ナビの形を1形式に固定）— 削除

変換器が対応できる形を有限個に保つため、ナビの書き方を1形式に固定していました。実測欄には**4つのナビのうち適合したのは1つだけ**とあり、既存デザインの多数派を通せない状態でした。

対処は[段3に記載](#ナビの形状どうすればできるようになるか)の通り、変換器側で引き取ります。ルールは削除します。

### L17（CSSセレクタの二重定義禁止）— 削除

変換器は CSS をそのまま複製するため、**変換上の根拠がありません。** 上書きは通常の技法であり、禁止すると共通CSSが肥大します。加えて現行構成では**一度も発火していません。**

### 混入を防ぐ仕組み

`vocabulary.md` の冒頭には設計原則として「**デザインは自由、構造は宣言必須**」と明記されています。それでもこの2本が入りました。

原因は、ルール表に**そのルールが変換のために必要な理由を書く欄がない**ことです。根拠のないルールが混ざっても表から判別できません。**列を1つ足せば、根拠が書けないルールは書いた時点で落ちます。**

## できないことを要件条項に変換した結果

| 事象 | 要件条項 |
|---|---|
| デザイン判断の自動修正が不可 | ツールは修正候補が複数ある時点で停止し、報告のみ行う。選ばない |
| 写真の上の文字が測定不能 | 目視確認項目として運用に置く。**デザインは変えない** |
| CI が無いと省略を防げない | CI があればマージ条件にする。無ければ検査結果ファイルを納品物に含める |
| 変換器の停止理由が事前に分からない | **まず変換器を拡張する。** デザイン側の制約は最後の手段であり、その場合は要合意 |

**「原理的に不可能」で終わる項目はありません。** 残るのは1点、デザインの決定は最初からツールが触らない領域として線を引く、という設計上の決定だけです。

## 付録. 用語

| 用語 | 意味 |
|---|---|
| PoC | 実現可能性の検証。本番向けではなく、確かめるために作ったもの |
| 制約検査（lint） | 書かれたコードが規約に沿っているかを自動で調べる仕組み |
| WCAG | ウェブのアクセシビリティの国際基準。本件は AA 準拠を対象とする |
| axe / pa11y | アクセシビリティを自動検査するツール。pa11y は axe を呼び出して使う |
| CI | コードを変更するたびに検査を自動実行する仕組み。違反があれば取り込みを止められる |
| PR | 変更を本体に取り込む前のレビュー単位 |
| コミットハッシュ | どの時点のコードかを一意に示す識別子 |
| ACF | WordPress でお客様が編集する入力欄を定義するプラグイン |
| CF7（Contact Form 7） | WordPress のフォーム作成プラグイン |
| CPT | 記事とは別に用意する投稿の種類（スポット・拠点・イベント等） |
| DOM | HTML の入れ子構造を指す言い方 |
| Walker | WordPress がメニューを HTML に変換する部品。差し替えられる |
| データ属性（`data-*`） | HTML に意味を書き添える標準の仕組み。見た目には影響しない |
