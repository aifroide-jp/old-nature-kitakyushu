# モックアップ作成方針 — 要約

Web サイト制作の進め方を変える提案です。
セットで読む資料: `prompts/mockup-generation.md`（実際の作成ルール）/ `REPORT.md`（検証の全記録）

---

## 1. 何を変えるのか

**モックアップを作るときのルールを決めます。それだけです。**

デザインは今まで通り自由。変えるのは「HTML の書き方」だけ。
これによって、モックアップから WordPress への変換が**コマンド1本で終わる**ようになります。

```
【今】 モックアップ ──→ AI が WordPress のコードを書く ──→ 人が全ページ確認
                        （毎回書き方が違う・静かに壊れる）

【提案】 ルールに沿ったモックアップ ──→ コマンドで変換 ──→ 壊れていたら止まる
                                        （毎回同じ結果・AI は介在しない）
```

---

## 2. なぜ必要か

現在の作り方では、**壊れていても誰も気づけません。**

本サイトで実際に起きていたこと（実測値）:

| 症状 | 実測 |
|---|---|
| 「活動ブログ」ページで、管理画面から編集できるはずの項目 | **14個中2個しか反映されていなかった** |
| 「活動拠点」ページで同じ問題 | **34個中22個** |
| イベント申し込み4ページ | **項目0個・フォーム未設置・リンク切れ** |

これらは検収を通過していました。**チェックの仕組みが「登録したか」しか見ておらず、「実際に画面に出ているか」を見ていなかった**ためです。

サイトの数が増えるほど、この「静かに壊れる」リスクは比例して増えます。

---

## 3. どう解決するか

モックアップの HTML に、**印を付けます。**

- ここは後から編集する箇所です
- ここは全ページ共通の部分です
- ここは記事一覧です

人間には見えない印なので、**デザインは1ピクセルも変わりません。**

印があると、変換プログラムが推測しなくて済みます。
そして**印が足りなければプログラムが停止し、中途半端なものを作りません。**
これが「静かに壊れる」を構造的になくす仕組みです。

---

## 4. 検証結果

本サイトのトップページで実際に試しました。

| 検証項目 | 結果 |
|---|---|
| デザインが変わっていないか | **900万ピクセル中、差分ゼロ** |
| 文章の取りこぼしがないか | **全223箇所を分類。行方不明ゼロ** |
| コマンドだけで WordPress になるか | **7ページ構成では成功**（PHP 26ファイル生成・項目217個すべて反映） |
| 実物のトップページで同じことができるか | **まだできない**（下記） |

### 正直に書く未達成事項

実物のトップページは、**メニュー（ナビゲーション）の書き方が原因で変換が止まります。**
原因は特定済みで、解決方針も決まっています（メニューの HTML 構造を1つに統一する）。
現時点で「実物サイトが丸ごとコマンドで変換できる」とは**まだ言えません。**

## 5. 経営判断のための材料

### 効果

| | 今 | 提案後 |
|---|---|---|
| 変換工程 | AI が全ページ分のコードを書く | **コマンド1本** |
| 品質のばらつき | 毎回違う | **毎回同じ**（同じ入力なら同じ結果） |
| 不具合の発見 | 人が全ページ目視（見落とす） | **壊れていたらプログラムが止まる** |
| 項目名の対応表作成 | 人が作る | **不要**（自動で一致する） |

### コスト

**この投資が効くのは「これから作るサイト」です。**

- **新規サイト**: 追加コストはほぼゼロ。モックアップを作る時にルールに従うだけ
- **既存サイトの移行**: **割に合いません。** 本サイトの場合、`style` 属性531個の書き換え、
  37ページ分の CSS 整理、7,407箇所のテキストについて「編集対象か否か」の判断が必要

サイトを継続的に作っていく前提であれば、ルールを整備する初期投資は回収できます。
1サイトだけのために導入するものではありません。

### リスク

- ルールは**守らせる仕組み（自動チェック）がなければ守られません。** 実際、AI に
  「アクセシビリティ基準を守って」と文章で指示しただけでは31件の違反が出ました。
  チェックを自動で回す運用まで含めて初めて機能します
- 未解決の項目が残っています（メニュー構造・一部のHTML要素の扱い）。`REPORT.md` 第6章に全件記載

## 6. お客様にご確認いただくこと

### 見え方は変わりません

デザイン・文言・レイアウトは今まで通りです。ご確認いただく内容も変わりません。

### 新しくお願いすること：「更新対象外リスト」のご確認

サイト公開後、**管理画面からご自身で変更できる箇所**と**できない箇所**が分かれます。
これは今までも同じでしたが、**今まではその境界が誰にも分からない状態**でした。

新しい方式では、モックアップ確認のタイミングで一覧をお出しします。

```
【更新対象外になる文言の例】
  「メインコンテンツへスキップ」        （読み上げ用の固定文）
  「所在地」「入場料」「開園時間」      （表の見出し）
  「見どころ・体験できること」          （セクション見出し）
```

**「この文言は後から変えたい」というものがあれば、この時点でお申し付けください。**
公開後の変更は、追加費用が発生する場合があります。

### アクセシビリティを先に確認します

福祉事業所として運営される以上、アクセシビリティ（誰でも使えること）は必須要件です。

従来は WordPress 化した後に確認していましたが、**モックアップの段階で確認します。**
理由は、後から直すとご確認いただいたデザインが変わってしまうためです。

本サイトでは、公開後の自動検査で**204件の基準違反**が検出されています。
その多くはモックアップの段階で作り込まれたもので、後戻りできない状態になっていました。
新しい方式では、この204件は**そもそも発生しません。**

## 7. 進め方

| 段階 | やること | 判断者 |
|---|---|---|
| 1 | ルールに沿ってモックアップを作成 | 制作側 |
| 2 | 自動チェック3種を通す（構造・アクセシビリティ・文章の網羅） | 機械 |
| 3 | **デザインのご確認** | **お客様** |
| 4 | **「更新対象外リスト」のご確認** | **お客様** |
| 5 | コマンドで WordPress に変換 | 機械 |
| 6 | 動作確認・納品 | 制作側 → お客様 |

段階2と5は機械が行うため、人による確認は段階3・4・6に集中します。

---

## 8. 現状と次にやること

**現状**: 検証用のブランチに一式を作成済み。Ichiki（変換の仕組み本体）にはまだ手を入れていません。
ルールが固まってから反映します。

**次の作業（優先順）**:

1. メニューの HTML 構造を統一する（実物サイト変換の唯一の障壁）
2. CSS の変数体系を統合する
3. 未定義の要素（動画埋め込み・パンくずリスト等）の扱いを決める

1が解決すれば、「実物サイトがコマンドで WordPress になる」と言えるようになります。

## 参考: 用語

| 用語 | 意味 |
|---|---|
| モックアップ | 完成イメージを HTML で作ったもの。デザインの合意に使う |
| WordPress | サイト公開後にお客様が内容を更新するための仕組み |
| ACF | WordPress で「ここを編集できます」という欄を作るプラグイン |
| CPT | 記事の種類。「自然スポット」「イベント」など同じ形式で増えていくページ |
| 自動チェック（lint） | ルールを守れているか機械が検査する仕組み |
