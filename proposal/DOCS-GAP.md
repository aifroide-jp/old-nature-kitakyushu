## 性質で分けると

### A. 生成物（機械が毎回作る）

`acf-map.yaml` とテーマとライブサイトを入力に、案件ごとに中身が変わるもの。

- C1 テスト仕様書（#3）… **実装あり**
- C3 検収シート（#6b）… **実装あり**
- C3 検収ガイド（#6）… 実装あり。**html 化と画像が無い**
- C2 リリース手順書（#5）… **実装なし**

### B. 手順書（人が読む。案件ごとにほぼ変わらない）

Ichiki 本体に1つ置いて、案件では原則そのまま使うもの。

- Ichiki セットアップ（#1）
- モックアップ作成（#2）
- Ichiki 実行・検証（#4）

**B は「案件ごとに生成する」必要が無い。** 本体に置いて参照すればよく、
案件固有の値（サイトURL・テーマ名）だけ差し込めばよい。

## #6 の html 化について

流れは `検証md → 検収ガイドmd → html`。

md を html にするだけなら小さいが、**画像を入れるなら実物のスクリーンショットが要る**。
これは既にある道具で撮れる。

```
scripts/visual-diff/diff.js   ← ライブサイトのフルページを撮っている（report/*.png）
proposal/visual-check/compare.js ← 同じく撮っている
```

「この画面のここを見てください」を**実際の画面で示せる**。手で貼るのではなく、
検収シートのページ一覧から自動で撮って埋め込む形にできる。

> ただし L1 が見るのは**完成したサイト**なので、撮影タイミングは
> テーマ投入後・コンテンツ投入後になる。生成の順序に依存する。

## #5 リリース手順書について

`rules/ichiki.md` は「エックスサーバー向けの手順書を自動出力する」と規定しているが実装が無い。

書くべき内容のうち、**機械が知っているもの**:

| 項目 | どこから取れるか |
|---|---|
| 必要プラグイン | `.ichiki.json` の `plugins_required` |
| 固定ページとテンプレートの対応 | `acf-map.yaml` の `pages[].page_type` / `page_id` |
| CPT とパーマリンク | `acf-map.yaml` の `cpt` |
| CF7 フォームと送信先 | 案件 `CLAUDE.md`「## フォーム設定」（未指定なら「送信先を設定」と明記する規定あり） |
| **未解決のまま残っているリンク** | 変換器の `--allow-unresolved-links` の警告 |

最後の行が今の宿題に直結する。**「まだ作っていないページ」を手順書に列挙**できれば、
`--allow-unresolved-links` を付けたまま先に進んでも、リリース時に取りこぼさない。

## 別件: data-section が編集画面の区切りに使われていない

`rules/ichiki.md` の食い違いを直す過程で見つけた**実装の抜け**。ルールの矛盾とは別。

旧方式は ACF の編集画面を3タブ（メインコンテンツ / セクション別 / 装飾要素）に分けていた。
振り分けは `HERO_RE = /(hero|main|top|kv|mv)/i` の部分一致で、これは推測なので削除した。

代わりに `data-section` があり、**実際のセクション名で分かれるので推測より正確**。
ところが生成された ACF に**タブフィールドが1つも出ていない**（`'type' => 'tab'` が0件）。

```
event の66フィールドが仕切りなしで平坦に並ぶ
hero_image / event_status / tag_1 / tag_2 / tag_3 / tag_4 / hero_title / event_date / …
```

情報は acf-map.yaml の `sections[].id` に入っているのに、使っていない。
**66件を仕切りなしで並べるのは L1 にとって辛い。** 検収の前に直したい。

やること: `inc/acf-<slug>.php` の生成時、セクションの切り替わりで
`array('type' => 'tab', 'label' => <セクション名>)` を挟む。

注意: セクション名は ASCII（`hero` / `detail` / `schedule`）なので、
**そのままタブ名にすると L1 に読めない**。日本語ラベルをどこから取るかは要検討
（モックの見出しテキストを使う案があるが、宣言が無い情報を推測することになる）。

## 後回し: AI が要るコマンドは /mockup と /retrofit（未着手）

**設計が反転していた。** Ichiki が用意していた `/setup` `/run` はどちらも機械的な
コマンドの羅列で、AI が判断する箇所が無かった。一方**本当に AI が要る仕事**である
「モックを書く」にはコマンドが無く、`prompts/mockup-generation.md`（530行）を
手で貼る運用だった。

| | 入力 | 出力 |
|---|---|---|
| `/mockup` | 要件（案件情報） | lint が通るモック |
| `/retrofit` | 制約なしモック | lint が通るモック（見た目を変えない） |

出力が同じで入力が違うだけなので、1コマンドの2モードでもよい。

### プロンプトが膨らむ問題への対処

語彙が育つほどプロンプトが膨らみ、1回で全部守るのが難しくなる
（実測: L31 と data-nav-current を足しただけで2節増えた）。

**巨大なプロンプトを1回渡す形にしない。lint が通るまで回す形にする。**

```
書く → ichiki lint → 指摘を直す → 通るまで繰り返す
```

これならプロンプトの網羅性への依存が下がる。今日の後付け実測（1ページ7分）が
この形で、lint の指摘がそのまま作業リストになった（L05 の53件は一括で処理できた）。

### 局面が2つある。混同しないこと

**モックは合意までに何度も触る。** 凍結物として扱うと設計を誤る。

| | 見た目 | 宣言 | 効く検査 |
|---|---|---|---|
| **合意前**（何度も触る） | **変わるのが正しい** | 保たれ続けないと困る | **lint だけ** |
| **後付け**（retrofit） | 変わってはいけない | これから付ける | lint ＋ ピクセル比較 |

合意前にピクセル比較をしても意味が無い（見た目を変えるのが目的だから）。
逆に後付けでは見た目が変わったら失敗なので、比較が絶対に要る。

**本当のリスクは「触るたびに宣言が腐る」こと。**
セクションを足して `data-section` を忘れる、文言を差し替えて `data-acf` を落とす、
`<head>` をいじって `<title>` を巻き込む。どれも静かに起きる。

実測: 後付け作業中に `<title>` を消した。**lint は通っていた**（a11y が捕まえた）。
lint だけでは足りない場面もある。

### だから /mockup は「1回生成するコマンド」ではない

```
要件 → 書く → lint → 見せる → 直す → lint → 見せる → … → 合意 → 変換
                ↑______________________|
                  ここが何周も回る
```

**触るたびに検査が走る形にする。** lint は 51ページで 0.42 秒（実測）なので、
編集ループに毎回入れても邪魔にならない。

未検討: 職員やデザイナーが HTML を直接編集する場合はコマンドを通らない。
pre-commit フックなど、**編集経路に依存しない止め方**が要るかもしれない。

### 副次的な利点

- 「vocabulary.md を読んでね」と毎回言わなくて済む（コマンドが読ませる）
- リポジトリ直下にモックが作られる（`.ichiki.json` の `mockup: "./"` と揃う）
